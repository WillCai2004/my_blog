pwn.college · shellcoding challenges

A rather unusual restriction on this challenge was that every byte of the shell code had to be unique – i.e., no byte could appear twice in the input shell code (up to 256 bytes, with no duplicate bytes). Inevitably, a full open/read/write will include repeated bytes (e.g. 0x0f05 , 0x31c0 , 0x00 ) -> the solution therefore has to have Two stages: stage 1 is a loader (with all distinct bytes), which loads an unconstrained stage 2.

⚠️ stage 1→stage 2 handoff not yet solved end-to-end: the general method is recorded but the specifics of how stage 1 communicates with stage 2 still needs refinement.

# 1. Mechanics of the problem

There is only a single input checked by the filter for whether or not every byte in the input is unique. Every normal shell code has far too many repeating bytes and is immediately rejected.

# 2. Overall methodology

  • stage 1 (loader with distinct bytes): loads the second stage from stdin (which we know is not subject to the same constraints) using a simple read(0, stage2_addr, 0x400); jmp stage2_addr . Each possible output of stage 1 is created by brute-forcing the landing address offset of stage 2 and checking if the length of the set of possible outputs equals the total number of distinct output bytes.
  • stage 2 (normal shell code): is loaded into memory by stage 1 and can then perform standard open/read/write operations.
  • how do you create stage 1's bytes uniquely? brute force stage 2 landing address offset: try each generated version of stage 1, and choose the first one where len(set) == len .

Stage2 logic: open("/flag", 0) → read(fd, rsp, 0x100) → write(1, rsp, n) → exit(0) .

# 3. Status/work left to do

  • the overall method works fine: a unique-byte stage 1 gets through the filter → reads a normal stage 2.
  • have not yet obtained Flag: the brute force for creating a unique-bytes stage 1 + finding correct landing address for stage 1 + creating the correct stage1->stage2 transition (read-size + timing + alignment of target for jmp rsi ) will need to be verified in a debugger.

# 4. Lessons learned (so far)

  • Two stages due to unique byte constraint: since the filter only examines the first segment, turn that segment into a small "mover" with all-distinct bytes, and bring in the real payload after examination.
  • creating small loader with all-distinct bytes: use compressed setup with cdq / push-pop /single-byte instrs, and brute force the address offset such that the four bytes of mov esi,imm32 are never among those used elsewhere — treat "uniqueness" as a searchable constraint
